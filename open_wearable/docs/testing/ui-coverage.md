# App user-journey coverage

This inventory defines tests that operate the real app through its user interface on a real phone, connected to real OpenEarables when a feature requires them. Patrol performs the taps, text entry, scrolling, navigation, and native-dialog interaction. The main assertion is the user-visible result of each action. Tests must not invoke a provider or BLE command in place of the UI action being tested.

The first target is Android. Repeat the applicable journeys on iPhone after the Android foundation works. This is a source-derived inventory, not evidence that the journeys currently pass. Add scenarios when exploratory use exposes additional states or interactions.

## Reading and maintaining this inventory

- **Planned** means a scenario has not yet been implemented as a phone test. When implemented, record its test path; passing requires a real run and its evidence. A widget/unit test alone does not complete a row here.
- **Implemented, unverified** means the complete automated path exists and builds, but still needs a real-phone run. **Partial, unverified** means the linked path covers only the stated subset. Neither status means passed.
- **Verified** means the linked automated path passed on the named real-phone environment. **Partial, verified** means the stated subset passed while the rest of the row remains planned. A pass on one phone/OS does not replace the device matrix.
- **None** means no earable is required; the real phone is always required. **One** means one identified test earable. **Pair** means known left/right earables. Other prerequisites name the capability or environment needed in addition.
- **UI** is suitable for automatic UI operation and assertions. **UI + fixture/manual** means an external condition, physical action, or observation is needed; record these separately so an automated tap is not reported as validation of sound, light, fit, or sensor accuracy.
- Expand a parameterized row into separate results for every supported option, sensor, channel, device, and relevant phone OS. A row is complete only when its applicable variants are covered.
- Record **not applicable** with the observed device capability and reason; do not silently pass a missing feature. Record **blocked** when a required capability, phone, permission state, or fixture is unavailable.
- Use test-created profiles, labels, recordings, and logs for destructive scenarios. Restore settings and disconnect test devices during cleanup; preserve failure evidence before cleanup.
- For each run keep app/library/firmware versions, phone and OS, target device IDs, case ID, outcome, failed step, screenshot, and relevant app/device logs. A feature opening successfully does not prove that its action succeeded.

Suggested order: implement startup/navigation, connect, configure/live data, and record journeys first; then settings/data management, capability-specific controls and mini-apps, then recovery and lifecycle combinations. Firmware installation, slot erase, and deliberate interrupted updates belong to an explicitly selected device-maintenance run with a recoverable test device.

## Capability and environment expansion checklist

Before claiming full coverage, collect the actual capabilities of the lab devices and expand the cases above for:

- Every exposed sensor/configuration, sampling-rate option, target option, profile type, and chart channel.
- Single earable, both stereo positions, combined/split pair, partial pair loss, and multiple independent devices.
- Listening modes, microphone source/gain controls, power modes, RGB/status LED combinations, battery metadata, edge recording, FOTA and image-slot capability presence/absence.
- Phone microphone and LE Audio inputs that are actually supported by the selected phone/OS/device combination.
- Fresh install, existing data, upgrade, granted/denied/permanently-denied permissions, Bluetooth disabled, no network, background/lock/resume, and process restart.
- Small-screen/large-text layouts and Android native permission/share/file/browser surfaces; corresponding iPhone surfaces later.
- Explicitly unavailable product capabilities (for example PPG on a particular device revision): keep the relevant feature untested/not applicable for that fixture rather than counting a disabled tile as its full functional coverage.

Source files may contain unused widgets or platform-specific branches. Add a phone journey only after confirming a real navigation path; retain a separate note for unreachable/dead UI if discovered. Physical sound quality, optical output, sensor measurement accuracy, and firmware algorithm correctness require separate checks and are not implied by a green UI test.
